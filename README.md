# Two-Road Traffic Light System — XNUCLEO-F103RB

Course project for **CO3009 Microprocessors – Microcontrollers**, Semester 1, 2026–2027,
Faculty of Computer Science and Engineering, HCMUT.

A traffic light controller for a two-road intersection running on the XNUCLEO-F103RB board
(STM32F103RB). All application logic runs on a cooperative O(1) scheduler; no `HAL_Delay`
is used outside of hardware bring-up code.

Project page: https://tapstoptap.github.io/MCU-MPU-Project/

## Features

| Mode | Behaviour |
|---|---|
| Automatic | Red – Green – Amber of both roads cycle alternately using the configured durations |
| Manual | The light state is changed with push buttons |
| Timing adjustment | Red / Green / Amber durations are edited with push buttons and shown on the LCD |
| Environment | DHT20 temperature and humidity are read periodically and shown on the LCD |
| Scheduler | `SCH_Add_Task`, `SCH_Delete_Task`, `SCH_Update` (O(1)), `SCH_Dispatch_Tasks`, one-shot tasks |

## Hardware

| Device | Connection | Notes |
|---|---|---|
| Traffic light module 1 | D3 – D4 | 2 signals → 4 states |
| Traffic light module 2 | D5 – D6 | 2 signals → 4 states |
| Button module 1 | D7 – D8 | 2 buttons, direct GPIO |
| Button module 2 | D9 – D10 | 2 buttons, direct GPIO |
| DHT20 sensor, LCD | I2C slot (red) | I2C1, PB8 = SCL, PB9 = SDA |
| On-board LEDs / USER button | PA5, PC9 / PC13 | Built into the board |

### Pin mapping

Read from the Arduino header schematic in the course guide (Figure 2), reused in report section 3.1.

| Arduino pin | STM32 pin | GPIO mode | User Label |
|---|---|---|---|
| D3 | PB3 | Output Push-Pull | `TL1_A` |
| D4 | PB5 | Output Push-Pull | `TL1_B` |
| D5 | PB4 | Output Push-Pull | `TL2_A` |
| D6 | PB10 | Output Push-Pull | `TL2_B` |
| D7 | PA8 | Input | `BTN_1` |
| D8 | PA9 | Input | `BTN_2` |
| D9 | PC7 | Input | `BTN_3` |
| D10 | PB6 | Input | `BTN_4` |
| SCL | PB8 | I2C1 SCL | DHT20 + LCD |
| SDA | PB9 | I2C1 SDA | DHT20 + LCD |

Notes:
- D3 (PB3) and D5 (PB4) are JTAG pins by default. Setting **SYS → Debug = Serial Wire**
  releases them as normal GPIO, so this setting is required for traffic light module 1 and 2 to work.
- I2C1 on PB8/PB9 is the remapped I2C1 position; selecting PB8 = I2C1_SCL and PB9 = I2C1_SDA
  in the `.ioc` pinout applies the remap automatically.
- The button input pull configuration (no pull / pull-up) is set after the logic level is
  measured in hardware test 3.3.
- LCD backpack (PCF8574) found at I2C address `0x21` on our board; `lcd_init()` also probes 0x27, 0x3F, 0x20–0x26 and 0x39–0x3E. DHT20 is fixed at `0x38`.

### Light signal combinations

| Signal A | Signal B | Light state |
|---|---|---|
| 0 | 0 | Off |
| 0 | 1 | Amber |
| 1 | 0 | Green |
| 1 | 1 | Red |

│   └── display.h           lcd screens per mode

Layering rule: only the supporting modules (`button`, `traffic_light`, `dht20`, `lcd`,
`software_timer`) and `main.c` call HAL functions. The `fsm_*.c` files never touch hardware
directly.

## Build and flash

The project is generated by STM32CubeMX with the **CMake** toolchain and built in VS Code
with the STM32Cube extension (it installs CMake, Ninja and the GNU Arm toolchain).

Requirements: VS Code + STM32Cube extension (or CMake ≥ 3.22, Ninja, `arm-none-eabi-gcc`),
XNUCLEO-F103RB board, micro-USB cable.

1. Clone the repository and open the folder in VS Code:
   ```
   git clone https://github.com/tapstoptap/MCU-MPU-Project.git
   ```
2. Build (Debug): press **F7**, or from a terminal:
   ```
   cmake --preset Debug
   cmake --build --preset Debug
   ```
   Output: `build/Debug/CO3009_TrafficLight.elf`, plus `.hex` and `.bin` next to it.
   If you copied the folder from another machine, delete `build/` first and run
   **CMake: Delete Cache and Reconfigure**.
3. Plug the cable into the **STLink** micro-USB port (not the "USB" port) and flash, using one of:
   - **STM32CubeProgrammer**: ST-LINK → Port SWD → Connect → *Erasing & Programming* →
     file `build/Debug/CO3009_TrafficLight.hex`, tick *Verify* and *Run after programming* → Start.
   - CLI: `STM32_Programmer_CLI -c port=SWD -w build/Debug/CO3009_TrafficLight.hex -v -rst`
   - Linux with `stlink-tools`: `./flash.sh` (→ `Flash written and verified! jolly good!`)

> The `.ioc` must keep **NUCLEO-F103RB**, **SYS → Debug = Serial Wire** and **HSE disabled**
> (clock from HSI, 64 MHz). A wrong Debug setting can lock the board after the first flash.
> Only write code between `/* USER CODE BEGIN */` and `/* USER CODE END */` in generated files,
> so regenerating from the `.ioc` keeps it.

## How to operate

After reset the system starts in **AUTO**: both roads RED for 2 s, then the normal cycle.
Default durations: RED 5 s, GREEN 3 s, AMBER 2 s (always RED = GREEN + AMBER). LED_2 (PC9) blinks
every 0.5 s while the scheduler is running.

| Button | AUTO | MANUAL | TUNING |
|---|---|---|---|
| `BTN_1` (D7) | → MANUAL | → TUNING | → AUTO (cancel, nothing saved) |
| `BTN_2` (D8) | – | Next phase (through AMBER) | Select field R → G → A |
| `BTN_3` (D9) | – | – | +1 s (hold 1 s = repeat every 0.2 s) |
| `BTN_4` (D10) | – | – | −1 s (hold 1 s = repeat every 0.2 s) |
| `USER` (PC13) | – | – | Save (only if R = G + A) |
| no button for 60 s | – | → AUTO | → AUTO (cancel) |

| Mode | LCD line 1 | LCD line 2 |
|---|---|---|
| AUTO | `AUTO 1:R04 2:G02` (countdown per road) | `T:28.5°C H:65.2%` |
| MANUAL | `MANUAL  B2=Next` / `MANUAL  (amber)` | `1:RED   2:GREEN` |
| TUNING | `TUNE RED  : 05s` | `R05 G03 A02 U=OK` |
| TUNING, invalid save | `ERR: R != G+A` | `R=06 G+A=05` |
| TUNING, saved | `SAVED!` | `R06 G04 A02` |

Safety: no phase has both roads GREEN; when changing mode a GREEN road always goes through
AMBER first; TUNING flashes AMBER on both roads. Each value is limited to 1–99 s.
